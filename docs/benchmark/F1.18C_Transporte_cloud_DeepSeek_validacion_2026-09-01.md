# F1.18C — Validación de transporte cloud DeepSeek

**Fecha:** 01-09-2026
**Estado:** COMPLETADA / PASS
**Entorno:** HP OMEN — WSL2 Ubuntu 24.04
**Python baseline:** 3.12.3
**Claude Code:** 2.1.252
**SDK Anthropic:** 0.120.0
**Etapa precedente:** F1.18B — Transporte cloud Anthropic (PASS)

## 1. Objetivo

Validar un segundo backend cloud para el Benchmark RAT utilizando DeepSeek, manteniendo los controles de aislamiento establecidos en F1.16 y F1.17.

La validación debe comprobar de forma independiente:

- conectividad controlada hacia DeepSeek dentro de SRT;
- bloqueo de Internet general;
- autenticación mediante credencial externa al repositorio;
- funcionamiento de la API nativa de DeepSeek;
- funcionamiento de la interfaz Anthropic-compatible;
- ejecución real de Claude Code utilizando DeepSeek como backend;
- ausencia de credenciales persistentes en el entorno al finalizar las pruebas.
## 2. Baseline inicial

F1.18C comenzó desde un estado controlado:

- repositorio `main` sincronizado y limpio;
- F1.18B cerrada con resultado PASS;
- Claude Code 2.1.252;
- Python 3.12.3;
- sin variables DeepSeek o Anthropic persistentes en el entorno;
- política SRT con únicamente los dominios Anthropic previamente autorizados.

Antes de modificar la allowlist se comprobó explícitamente el acceso a `api.deepseek.com`.

SRT respondió:

`HTTP/1.1 403 Forbidden`

`X-Proxy-Error: blocked-by-allowlist`

**Control negativo previo: PASS**

## 3. Gestión de credenciales

La API key de DeepSeek se almacenó fuera del repositorio en:

`/home/cumplebench/runtime/deepseek/api-key`

El directorio utiliza permisos `700` y el archivo de credencial permisos `600`.

La credencial se carga únicamente durante cada prueba y posteriormente se elimina de la variable de entorno utilizada.

Al finalizar F1.18C se comprobó que no permanecieran variables de autenticación persistentes.

Durante el diagnóstico inicial se utilizó accidentalmente una credencial que no correspondía a una API key válida de DeepSeek. Las respuestas HTTP 400 obtenidas con esa credencial se consideran pruebas diagnósticas inválidas y no forman parte del resultado del benchmark.

La credencial correcta fue validada estructuralmente antes de repetir las pruebas, sin registrar ni mostrar su contenido.

## 4. Ampliación mínima de allowlist

Se agregó exclusivamente:

`api.deepseek.com`

La allowlist resultante quedó limitada a:

- `api.anthropic.com`
- `platform.claude.com`
- `api.deepseek.com`

Se mantuvieron sin cambios:

- `allowUnixSockets: []`
- `allowLocalBinding: false`

No se habilitó acceso general a Internet.
## 5. Validación de red

Después de incorporar `api.deepseek.com` a la allowlist se repitió la prueba desde SRT.

DeepSeek permitió establecer la conexión y respondió HTTP 401 al realizar una solicitud sin autenticación. Esto confirma que la conexión alcanzó el servicio y no fue bloqueada por SRT.

Como control negativo se intentó acceder desde el mismo entorno a `https://example.com`.

SRT respondió:

`HTTP/1.1 403 Forbidden`

`X-Proxy-Error: blocked-by-allowlist`

**Resultado de aislamiento de red: PASS**

## 6. API nativa DeepSeek

Con la credencial correcta se realizó una llamada autenticada desde SRT a:

`https://api.deepseek.com/chat/completions`

utilizando el modelo:

`deepseek-v4-pro`

DeepSeek respondió:

`HTTP=200`

La respuesta identificó explícitamente:

`"model":"deepseek-v4-pro"`

La prueba utilizó `max_tokens=20`. Los 20 tokens de salida fueron consumidos por `reasoning_content`, por lo que la respuesta terminó con `finish_reason: length` antes de producir contenido final.

Esto no constituye una falla del transporte: la solicitud fue autenticada, procesada por `deepseek-v4-pro` y respondió HTTP 200.

**API nativa DeepSeek: PASS**

## 7. Interfaz Anthropic-compatible

Se realizó posteriormente una prueba independiente utilizando:

- SDK Anthropic 0.120.0;
- endpoint `https://api.deepseek.com/anthropic`;
- modelo `deepseek-v4-pro`;
- ejecución dentro de SRT.

La respuesta obtenida fue:

`TYPE: message`

`MODEL: deepseek-v4-pro`

`TEXT: F1.18C-SDK-OK`

**Interfaz Anthropic-compatible: PASS**
## 8. Claude Code utilizando DeepSeek

La validación final ejecutó Claude Code 2.1.252 dentro de SRT utilizando:

- `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic`;
- autenticación mediante `ANTHROPIC_AUTH_TOKEN`;
- DeepSeek V4 Pro como backend principal;
- configuración runtime aislada de Claude Code;
- `--permission-mode dontAsk`;
- `--no-session-persistence`;
- `--no-chrome`;
- `--disable-slash-commands`.

El prompt controlado solicitó responder exactamente:

`F1.18C-DEEPSEEK-OK`

Claude Code respondió:

`F1.18C-DEEPSEEK-OK`

**Claude Code → DeepSeek: PASS**

## 9. Advertencias de compatibilidad observadas

Durante la ejecución correcta Claude Code emitió las advertencias:

`[claude-code:unrecognized_model] {"model":"deepseek-v4-flash","query_source":"generate_session_title"}`

y:

`[claude-code:unrecognized_model] {"model":"deepseek-v4-pro[1m]","query_source":"sdk"}`

Estas advertencias deben conservarse como una observación técnica del benchmark.

No impidieron la inferencia solicitada: después de ambas advertencias Claude Code produjo correctamente:

`F1.18C-DEEPSEEK-OK`

Por tanto, en esta versión de Claude Code las advertencias no se consideran una falla del transporte, aunque deberán mantenerse registradas para evaluar reproducibilidad y futuras versiones del cliente.

También apareció una advertencia indicando que los conectores `claude.ai` estaban deshabilitados porque la fuente de autenticación externa tenía precedencia sobre el login de `claude.ai`.

Este comportamiento es coherente con la ejecución mediante un backend externo y no afectó la prueba.

## 12. Resultado

**F1.18C — transporte cloud DeepSeek: PASS**

Se validó el funcionamiento real de DeepSeek como segundo backend cloud del Benchmark RAT mediante tres niveles independientes:

1. API nativa de DeepSeek;
2. interfaz Anthropic-compatible mediante SDK;
3. Claude Code ejecutado dentro de SRT utilizando DeepSeek como backend.

La incorporación de DeepSeek requirió agregar únicamente `api.deepseek.com` a la allowlist.

Internet general permaneció bloqueado y no fue necesario habilitar Unix sockets, localhost ni local binding.

Las advertencias `unrecognized_model` observadas en Claude Code 2.1.252 quedan registradas como una limitación de compatibilidad a vigilar, pero no impidieron completar correctamente la inferencia.
