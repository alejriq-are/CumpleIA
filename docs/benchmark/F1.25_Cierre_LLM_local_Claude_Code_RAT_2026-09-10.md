ni demuestran que 16K alcance para el prompt real de Claude Code.

## Transporte, SRT y Claude Code

| Prueba | Generación observada |
|---|---:|
| `/v1/chat/completions`, tres ejecuciones | 37.17 / 42.88 / 41.18 tok/s |
| `/v1/messages`, tres ejecuciones | 42.76 / 42.90 / 41.14 tok/s |
| `/v1/messages`, promedio | 42.27 tok/s |
| `/v1/messages` vía SRT, promedio | 43.05 tok/s |
| Claude Code + SRT + `--name` | 41.56 tok/s |

No se observó degradación relevante entre `/v1/chat/completions` y
`/v1/messages`, ni al incorporar SRT. Las diferencias de estas muestras
se interpretan como variación observada, sin atribuir una aceleración a SRT.

Claude Code inicialmente lanzó dos requests concurrentes, incluida la auxiliar
de título (`generate_session_title`), con aproximadamente 29–30 tok/s por slot.
Con `--name` quedó una petición activa: 482 tokens generados a **41.56 t/s**,
11.91131 s totales, sin truncamiento. El prompt eval de esa prueba procesó
sólo 4 tokens por reutilización de caché; no mide prefill completo.
Desactivar el título se incorporó después al entorno del harness como
`CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`. Es una calibración para evitar la
request auxiliar, no una optimización del modelo. Los 41.56 t/s corresponden
a la prueba controlada con `--name`, no a la media de F1.25-B.

### Compatibilidad del template Jinja

El template original rechazaba mensajes `system` intercalados con
`System message must be at the beginning`. Se usó una copia externa
`qwen36-claude-code.jinja`: el primer `system` se renderiza una sola vez y
los posteriores se renderizan en su posición original, sin descartarlos ni
moverlos al inicio. El parche permitió completar la prueba de Claude Code.
Se documenta esa intervención de runtime sin modificar el GGUF en este cierre.

### Trazabilidad del cambio trusted

La intervención histórica afectó `candidate_environment()` de
`docs/benchmark/runner/trusted/run_benchmark.py`, incorporando explícitamente
`CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` al entorno que recibe Claude Code.
Exportarla sólo en el shell no bastaba porque el harness construye ese entorno.

- Test histórico: `./.venv/bin/python -m pytest docs/benchmark/runner/trusted/test_run_benchmark.py -q`.
- Resultado reportado: **16 passed in 0.04s**.
- SHA-256 reportado del `run_benchmark.py` modificado:
  `583e5d5ce949de7fb95ef68ecec1ed351098444fae1255eeb60918240fefdc5c`.

Este hash identifica el archivo de la ejecución histórica, no el árbol actual
ni un manifest completo. Este cambio documental no aplica ni altera el parche
del harness y no vuelve a ejecutar esos tests.

### F1.25-A: calibración conservada

El request inicial contenía **23,315 tokens (23315)** y excedió los 16384
disponibles; el servidor respondió HTTP 400 antes de implementar la tarea.
Separadamente, Docker estaba apagado y el verifier falló en `docker network`.
El `result.json` reportó `trustedChecksPassed=null`, mientras que
`verification.json` reportó `trustedChecksPassed=false` y `HARNESS_ERROR`.
Se conserva como calibración de contexto e infraestructura, sin convertirla
en una medición de calidad funcional del modelo.

### F1.25-B: ejecución completada, FAIL formal

Con 64K, el agente terminó con exit 0, sin timeout, en **630.223109 s**.
Los checks generales de infraestructura, RLS, catálogo, configuración y
fixture pasaron. Esto no equivale a aprobar el perfil contractual completo.

El verifier falló por una regex nominal que exige `organizaciones[0]`, aunque
el helper usa `memberships[0]` como fallback después de buscar la membresía.
Ese rechazo nominal es un falso negativo para la semántica del helper; se
conserva el **FAIL formal**, sin renombrar variables ni recalibrar el verifier
retrospectivamente para aprobar esta solución.

La revisión también detectó defectos funcionales reales:

- El selector filtra opciones ante un parámetro `organization` inválido,
  en lugar de mantener disponibles todas las membresías para elegir.
- `AutodiagnosticoWorkspace` inicializa `orgId` desde la prop `organizationId`,
  pero no sincroniza cambios posteriores de esa prop. El callback del selector
  interno no resuelve la actualización desde el padre/URL.
- Los tests generados duplican el helper en JavaScript y no importan el módulo
  TypeScript real; su PASS no prueba esa implementación ni su integración.
