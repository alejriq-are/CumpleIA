# F1.18A — Contrato común de transporte de candidatos

**Fecha:** 01-09-2026
**Estado:** IMPLEMENTADA / PENDIENTE DE VALIDACIÓN DE BACKENDS
**Entorno de referencia:** HP OMEN — WSL2 Ubuntu 24.04
**Etapas precedentes:** F1.16 SRT (PASS), F1.17 Managed Settings (PASS)

## 1. Objetivo

Definir una interfaz de configuración única para seleccionar el transporte al modelo sin cambiar el workspace, las herramientas, los permisos administrados, la política SRT ni el futuro harness de evaluación.

F1.18A define el contrato. No valida todavía conectividad con un proveedor concreto.

## 2. Archivos de referencia

- Esquema normativo: `docs/benchmark/runner/transport-contract.schema.json`
- Ejemplo sin secretos: `docs/benchmark/runner/candidate-transport.example.json`

El esquema es la fuente de verdad para la forma y las restricciones básicas de la configuración. El ejemplo solo demuestra su uso y no identifica un candidato definitivo.

## 3. Contrato

Cada ejecución debe resolver exactamente una configuración con estos campos:

| Campo | Tipo | Regla |
|---|---|---|
| `candidateName` | string | Nombre lógico estable y único dentro del benchmark. No es el model ID. |
| `backendClass` | `cloud` o `local` | Clasifica el transporte sin modificar las demás condiciones experimentales. |
| `provider` | string | Identificador estable del proveedor o adaptador. |
| `endpoint` | URI HTTP(S) absoluta | Endpoint base consumido por el cliente del candidato. No implica autorización de red. |
| `modelId` | string | Identificador exacto enviado al proveedor. No se usan alias implícitos del runner. |
| `credentialEnv` | string o `null` | Nombre de la variable de entorno que contiene la credencial. Nunca el secreto. `null` significa que el backend no requiere autenticación. |
| `timeoutSeconds` | entero | Timeout por solicitud, entre 1 y 3600 segundos. |

No se admiten propiedades adicionales. Los siete campos son obligatorios, incluido `credentialEnv` cuando su valor sea `null`.

## 4. Resolución y secretos

El runner futuro deberá:

1. validar la configuración contra el esquema antes de iniciar al candidato;
2. resolver `credentialEnv` únicamente desde el entorno trusted de ejecución;
3. fallar de forma cerrada si se declara una variable y no está definida;
4. no imprimir, persistir, incorporar al workspace ni pasar el valor secreto como argumento de línea de comandos;
5. registrar para trazabilidad los campos no secretos y si la credencial fue requerida, nunca su valor.

Los archivos reales por candidato podrán versionarse solo si contienen nombres de variables, no credenciales.

## 5. Comparabilidad cloud/local

`backendClass` permite analizar candidatos cloud y local sin bifurcar el protocolo. Ambos reciben el mismo contrato, timeout explícito y nombre lógico; cambian únicamente los valores del transporte.

Las siguientes condiciones permanecen invariantes entre candidatos:

- Python 3.12.3;
- versión del proyecto y dependencias;
- workspace inicial y tarea;
- Claude Code y managed settings;
- herramientas disponibles y permisos;
- política SRT y controles de filesystem;
- harness, límites, captura de resultados y evaluación.

Una diferencia necesaria de allowlist o encaminamiento se tratará como propiedad del transporte y deberá validarse y registrarse en F1.18B/F1.18C. No puede introducir cambios encubiertos en managed settings, herramientas o harness.

## 6. Relación con SRT y managed settings

Este contrato no concede conectividad. `endpoint` declara el destino lógico, pero SRT sigue siendo la autoridad efectiva de red.

F1.18A no modifica:

- `/etc/cumpleia-benchmark/srt-prefinal.json`;
- `docs/benchmark/runner/managed-settings.json`;
- `/etc/claude-code/managed-settings.json`;
- bloqueo de Internet general, localhost o sockets Unix;
- herramientas bloqueadas o autorizadas.

La credencial tampoco se añade a managed settings. Su inyección y alcance deberán definirse en el runner trusted sin exponerla a archivos del candidato.

## 7. Límites de esta etapa

Queda expresamente fuera de F1.18A:

- instalar o configurar Ollama, Qwen u otro servidor/modelo local;
- elegir modelos o proveedores definitivos;
- probar endpoints o credenciales;
- modificar allowlists, proxy, localhost, sockets o binding local;
- implementar el runner/harness persistente;
- ejecutar pruebas de desempeño o calidad.

## 8. Criterios de aceptación

F1.18A queda implementada documentalmente cuando:

- el esquema exige proveedor, endpoint, model ID, referencia de credencial, timeout y nombre lógico;
- cloud y local usan la misma estructura;
- no hay secretos en los archivos versionados;
- Python 3.12.3 queda fijado como baseline común;
- SRT y managed settings permanecen sin cambios;
- el ejemplo valida contra el esquema;
- `git diff --check` no informa errores.

La validación de conectividad queda pendiente para F1.18B (cloud) y F1.18C (local).
