# F1.19B — Workspace reproducible y aislamiento del repositorio canónico

**Fecha:** 2026-09-02
**Estado:** EN DISEÑO

## 1. Objetivo

Implementar y validar el mecanismo mediante el cual cada corrida del benchmark se ejecuta sobre un workspace efímero creado desde un `baselineCommit` conocido.

El candidato no debe trabajar directamente sobre el repositorio canónico de CumpleIA.

## 2. Repositorio canónico

El repositorio utilizado como fuente trusted del baseline es:

~~~text
/home/cumplebench/projects/CumpleIA
~~~

Durante una corrida del benchmark este repositorio no debe ser writable por el candidato.

El harness utiliza el repositorio canónico únicamente como fuente para construir un workspace reproducible desde el commit solicitado.

## 3. Workspace efímero

Cada corrida utiliza un directorio independiente con la forma:

~~~text
/home/cumplebench/benchmark-workspaces/<runId>
~~~

El harness es responsable de:

- crear el workspace;
- materializar exactamente el `baselineCommit`;
- verificar que el estado inicial sea limpio;
- registrar el commit efectivo;
- eliminar o conservar el workspace según la política posterior del benchmark.

El candidato solo puede modificar el workspace correspondiente a su corrida.

## 4. Evidencia trusted

La evidencia de cada corrida se almacena separadamente:

~~~text
/home/cumplebench/benchmark-runs/<runId>
~~~

Este directorio es administrado exclusivamente por el harness trusted.

El candidato no debe tener permiso de escritura sobre esta ruta.

## 5. Política SRT por corrida

La política histórica:

~~~text
/etc/cumpleia-benchmark/srt-prefinal.json
~~~

se conserva sin modificaciones como evidencia de F1.16–F1.18.

F1.19 genera una política SRT específica para cada corrida.

La política efectiva debe permitir escritura únicamente en:

~~~text
/home/cumplebench/benchmark-workspaces/<runId>
/home/cumplebench/benchmark-runtime/<runId>/tmp
/home/cumplebench/benchmark-runtime/<runId>/claude
~~~

El repositorio canónico no debe aparecer en `allowWrite`.

El directorio de evidencia tampoco debe aparecer en `allowWrite`.

## 6. Generación trusted de la política

La política de corrida es generada por el harness antes de iniciar al candidato.

El candidato no puede proporcionar ni modificar el archivo de settings SRT.

El archivo generado debe quedar fuera del workspace writable del candidato.

El harness debe registrar un hash SHA-256 de la política efectiva utilizada.

## 7. Prueba de capacidad SRT

Se verificó que Sandbox Runtime acepta un archivo de settings alternativo mediante `--settings` sin modificar la política histórica.

Resultado:

~~~text
F1.19B-SRT-SETTINGS-OK
~~~

Esto permite utilizar una política distinta por corrida manteniendo intacto `srt-prefinal.json`.

## 8. Invariantes de aislamiento

Una corrida válida debe demostrar que:

- el candidato puede escribir en su workspace;
- el candidato no puede escribir en el repositorio canónico;
- el candidato no puede escribir en el directorio de evidencia;
- otro workspace de una corrida distinta no es writable;
- la política SRT efectiva corresponde al `runId`;
- el baseline del workspace coincide con el commit solicitado;
- el workspace comienza con estado Git limpio.

## 9. Criterio fail-closed

Si el harness no puede garantizar alguno de los invariantes anteriores, la corrida debe terminar como `HARNESS_ERROR`.

## 10. Siguiente implementación

F1.19B implementará primero la creación reproducible del workspace y luego la generación de la política SRT específica de corrida.

Se creó un workspace efímero mediante `git worktree` desde el commit:

~~~text
2159753243225471b73e97f670b457c5f2eeee23
~~~

Ruta utilizada:


El workspace quedó en `detached HEAD`, con el commit exacto solicitado y estado Git inicial limpio.

Se verificó además que una modificación realizada en el workspace no apareció en el repositorio canónico.

## 12. Validación de aislamiento SRT

Se generó una política SRT temporal específica para la corrida de prueba.

La política permitió escritura en:

~~~text
/home/cumplebench/benchmark-workspaces/f119b-workspace-test

/home/cumplebench/benchmark-runtime/<runId>/claude
~~~

Esto demuestra que el candidato puede modificar únicamente su workspace mientras el repositorio canónico y la evidencia permanecen protegidos por SRT.

## 14. Aislamiento Git definitivo

La prueba inicial con `git worktree` permitió validar la materialización exacta del commit y la separación de archivos de trabajo.

Sin embargo, se constató que un worktree mantiene un archivo `.git` que referencia metadatos ubicados dentro del repositorio canónico:

~~~text
gitdir: /home/cumplebench/projects/CumpleIA/.git/worktrees/f119b-workspace-test
~~~

Por esta razón, `git worktree` no se adopta como mecanismo definitivo del harness.

El workspace definitivo se materializará mediante:

~~~text
git clone --no-hardlinks --no-checkout <repo-canónico> <workspace>
git -C <workspace> checkout --detach <baselineCommit>
git -C <workspace> remote remove origin
~~~

La validación realizada confirmó:

~~~text
COMMIT EXACTO: PASS
STATUS LIMPIO: PASS
.git INDEPENDIENTE: PASS
REMOTES AUSENTES: PASS
ALTERNATES AUSENTES: PASS
OBJETOS HARDLINKED: 0
~~~

Esto evita que el workspace dependa de los metadatos Git del repositorio canónico y proporciona una segunda capa de aislamiento adicional a SRT.

El mecanismo normativo de F1.19B será, por tanto, un clon Git independiente sin hardlinks, sin alternates y sin remote hacia el repositorio canónico.

## 15. Validación automatizada de fronteras SRT

El harness trusted generó una política SRT específica para la corrida:

~~~text
/home/cumplebench/benchmark-runs/f119b-srt-policy-test/srt-settings.json
~~~

La política fue creada con permisos `0600` y su `allowWrite` quedó limitado a:

~~~text
/home/cumplebench/benchmark-workspaces/f119b-srt-policy-test
/home/cumplebench/benchmark-runtime/f119b-srt-policy-test/tmp
/home/cumplebench/benchmark-runtime/f119b-srt-policy-test/claude
~~~

El repositorio canónico y el directorio de evidencia no forman parte de las rutas permitidas para escritura.

La ejecución real dentro de SRT produjo:

~~~text
WORKSPACE WRITE: PASS
RUNTIME TMP WRITE: PASS
CANONICAL WRITE BLOCKED: PASS
EVIDENCE WRITE BLOCKED: PASS
~~~

Los intentos de escritura sobre el repositorio canónico y la evidencia fallaron con `Read-only file system`.

Resultado: PASS.

Resultado: PASS.
