# F1.19A — Contrato y estructura del harness reproducible

**Fecha:** 2026-09-02
**Estado:** PASS (contrato 1.0 implementado; ampliado por F1.19D)

## 1. Objetivo

Definir el contrato estable del harness confiable utilizado por el benchmark CumpleIA.

F1.19A no implementa todavía la ejecución de candidatos. Su objetivo es fijar formalmente:

- entradas de una corrida;
- salidas autoritativas;
- estados posibles;
- frontera trusted/untrusted;
- estructura de evidencia;
- relación con el contrato de transporte definido en F1.18A;
- invariantes de reproducibilidad y seguridad.

El diseño debe permitir ejecutar distintos candidatos —cloud o local— sin modificar la lógica de evaluación confiable.

## 2. Principio de confianza

El harness se ejecuta fuera del Sandbox Runtime del agente y constituye parte del Trusted Computing Base del benchmark.

El agente/candidato se considera no confiable.

Por tanto:

~~~text
HARNESS / VERIFICADORES / FIXTURES / CREDENCIALES TRUSTED
                         |
                         | controla
                         v
                    Sandbox Runtime
                         |
                         v
                  agente / candidato
                         |
                         v
                 workspace efímero
~~~
El agente no puede decidir el resultado de la corrida ni modificar los verificadores confiables.
Un mensaje del agente indicando que una prueba pasó no constituye evidencia autoritativa.
Solo los checks ejecutados por el harness fuera del sandbox pueden determinar PASS o FAIL.
## 3. Separación de responsabilidades
F1.19A mantiene separados los siguientes contratos:
### 3.1 Transporte del candidato
El transporte ya está definido por:
docs/benchmark/runner/transport-contract.schema.json
F1.19 no duplica campos específicos de Anthropic, DeepSeek o llama-server.
Cada corrida referencia una configuración que cumple dicho contrato.
### 3.2 Configuración de corrida
La configuración de corrida define qué debe ejecutar el harness y bajo qué condiciones reproducibles.
Artefacto previsto:
docs/benchmark/runner/run-config.schema.json
### 3.3 Resultado autoritativo
El resultado final de una corrida debe poder ser interpretado automáticamente sin depender de logs narrativos.
Artefacto previsto:
docs/benchmark/runner/run-result.schema.json
### 3.4 Evidencia
Los logs y resultados intermedios son evidencia de soporte, pero no sustituyen al resultado estructurado final.
## 4. Contrato de entrada de una corrida
Cada corrida debe partir de una configuración estructurada validable mediante JSON Schema.
Los campos mínimos son:
### 4.1 schemaVersion
Versión del contrato del harness.
Permite evolucionar el formato manteniendo trazabilidad de corridas históricas.
La versión inicial será:
~~~text
1.0
~~~

### 4.2 runId

Identificador único de la corrida.

Debe permitir correlacionar configuración, workspace, logs, verificaciones y resultado final.

`run-config.schema.json` describe la configuración efectiva materializada por el harness, por lo que `runId` es obligatorio en dicho artefacto.

Cuando el operador no proporcione un identificador, el harness debe generarlo antes de validar y persistir la configuración efectiva.
### 4.3 candidateName
Nombre lógico del candidato sometido al benchmark.
Este valor identifica al candidato para efectos de evidencia y comparación, pero no define directamente el proveedor ni el modelo.
### 4.4 baselineCommit
Commit Git exacto desde el cual debe construirse el workspace inicial.
No se permite utilizar implícitamente el estado actual de una rama como baseline.
El harness deberá verificar que el commit solicitado existe antes de iniciar la corrida.
### 4.5 workspace administrado por el harness

La raíz y la ubicación concreta del workspace no forman parte de la configuración controlable por una corrida.

El harness trusted determina el directorio de workspaces y genera un workspace efímero independiente para cada `runId`.

El candidato no debe trabajar directamente sobre el repositorio canónico de desarrollo.

### 4.6 transportConfig
Referencia a la configuración de transporte del candidato.
Dicha configuración debe cumplir:
docs/benchmark/runner/transport-contract.schema.json
El harness no debe incorporar lógica específica de proveedor en el contrato general de corrida.
### 4.7 taskFile

Ruta relativa al repositorio canónico de la tarea autoritativa entregada al
candidato. F1.19D incorporó este campo como obligatorio para que el prompt sea
reproducible y quede preservado, junto con su SHA-256, en la evidencia de la
corrida. No se aceptan rutas absolutas ni escapes fuera del repositorio
canónico.

### 4.8 timeoutSeconds
Tiempo máximo permitido para la ejecución del agente.
El timeout es controlado por el harness trusted y no por el candidato.
### 4.9 verificationProfile
Identificador del conjunto de verificaciones confiables que deben ejecutarse después de la intervención del agente.
El perfil permite que distintas tareas del benchmark utilicen diferentes verificadores sin modificar el contrato general del harness.
## 5. Estados autoritativos de una corrida
Toda corrida debe finalizar exactamente en uno de los siguientes estados:

~~~text
PASS
FAIL
TIMEOUT
HARNESS_ERROR
~~~

### 5.1 PASS
El agente terminó dentro del tiempo permitido y todas las verificaciones confiables requeridas fueron satisfactorias.
El exit code del agente por sí solo no determina PASS.
### 5.2 FAIL
El harness pudo ejecutar correctamente la corrida y las verificaciones, pero uno o más criterios confiables no fueron satisfechos.
También puede utilizarse cuando el agente finaliza sin producir una solución verificable.
### 5.3 TIMEOUT
El candidato excedió el tiempo máximo autorizado.
El harness debe terminar el proceso controladamente y preservar la evidencia disponible.
Una corrida TIMEOUT nunca puede considerarse PASS aunque el workspace contenga cambios parciales correctos.
### 5.4 HARNESS_ERROR
La infraestructura confiable no pudo garantizar una corrida válida.
Ejemplos:
- no fue posible preparar el baseline;
- falló el reset de la base de datos;
- no pudo ejecutarse un verificador obligatorio;
- se perdió evidencia requerida;
- ocurrió una inconsistencia interna del harness.
HARNESS_ERROR representa un problema del entorno de evaluación y no debe contabilizarse como fallo funcional del candidato.
## 6. Contrato de resultado autoritativo

Cada corrida debe producir un archivo estructurado `result.json`.

Este archivo es generado exclusivamente por el harness trusted y constituye la fuente autoritativa del resultado de la corrida.

Como mínimo debe registrar:

### 6.1 Identidad

- `schemaVersion`
- `runId`
- `candidateName`
- `baselineCommit`

### 6.2 Estado de ejecución

- `status`
- `agentExitCode`
- `timedOut`
- `trustedChecksPassed`

`status` solo puede tomar uno de los valores definidos en la sección 5.

`agentExitCode` puede ser nulo cuando el proceso no llegó a iniciarse correctamente.

`trustedChecksPassed` solo puede ser verdadero cuando todos los verificadores obligatorios terminaron correctamente y sus criterios fueron satisfechos.

### 6.3 Tiempos

El resultado debe registrar al menos:

- `startedAt`
- `finishedAt`
- `durationSeconds`

Los timestamps deben expresarse en UTC utilizando formato ISO 8601.

### 6.4 Integridad del baseline

El harness debe registrar el commit utilizado para crear el workspace.

Cuando corresponda, también debe poder registrar el estado Git posterior a la intervención del agente, pero dicho estado no reemplaza al baseline original.

## 7. Estructura de evidencia

Cada corrida debe producir un directorio de evidencia independiente.

La estructura mínima prevista es:

~~~text
benchmark-runs/
└── <runId>/
    ├── run.json
    ├── transport.json
    ├── baseline.json
    ├── agent.stdout.log
    ├── agent.stderr.log
    ├── verification.json
    ├── tests.log
    ├── result.json
    └── manifest.sha256
~~~

La implementación podrá agregar archivos adicionales siempre que no modifique el significado de los artefactos mínimos.

### 7.1 run.json

Snapshot de la configuración efectiva utilizada para iniciar la corrida.

No debe contener secretos.

### 7.2 transport.json

Snapshot de la configuración de transporte validada contra el contrato F1.18A.

Solo registra el nombre de la variable de entorno de credencial, nunca el valor secreto.

### 7.3 baseline.json

Registra información suficiente para demostrar desde qué estado reproducible comenzó la corrida.

Como mínimo debe incluir el commit Git utilizado.

### 7.4 agent.stdout.log y agent.stderr.log

Captura realizada por el harness desde fuera del sandbox.

Estos archivos son evidencia de diagnóstico y no constituyen por sí mismos un resultado autoritativo.

### 7.5 verification.json

Resultado estructurado de las verificaciones confiables ejecutadas fuera del sandbox.

Su estructura detallada se definirá en F1.19C.

### 7.6 tests.log

Salida textual de pruebas y verificaciones confiables cuando corresponda.

### 7.7 result.json

Resultado autoritativo final definido en la sección 6.

### 7.8 manifest.sha256

Manifest de integridad generado por el harness sobre los artefactos de evidencia.

El candidato no debe tener permisos para modificar este directorio.

## 8. Frontera trusted/untrusted

La frontera de seguridad del harness debe cumplir los siguientes principios.

El candidato puede modificar únicamente su workspace efímero y los recursos explícitamente habilitados para la ejecución.

El candidato no debe poder escribir en:

- repositorio canónico utilizado como fuente del baseline;
- implementación del harness;
- perfiles de verificación;
- fixtures confiables;
- directorio de evidencia;
- configuración SRT administrada;
- managed settings;
- credenciales trusted.

Las credenciales requeridas por un transporte se resuelven fuera del workspace y se inyectan al proceso de ejecución únicamente cuando son necesarias.

El valor de una credencial nunca debe persistirse en `run.json`, `transport.json`, logs o resultados.

## 9. Invariantes de reproducibilidad

Dos candidatos comparados bajo una misma tarea deben utilizar:

- el mismo baseline commit;
- el mismo perfil de verificación;
- el mismo estado inicial de base de datos;
- las mismas restricciones SRT;
- el mismo límite temporal definido para la ronda;
- los mismos fixtures y verificadores confiables.

Las diferencias propias del transporte, proveedor o modelo se expresan exclusivamente mediante la configuración de transporte.

## 10. Regla fail-closed

Si el harness no puede demostrar que el baseline, el reset, las verificaciones o la evidencia son confiables, la corrida debe terminar como `HARNESS_ERROR`.

El harness nunca debe inferir PASS a partir de una respuesta textual del agente ni continuar silenciosamente cuando falla un componente trusted.
