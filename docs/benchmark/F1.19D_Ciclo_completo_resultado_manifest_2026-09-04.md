# F1.19D — Ciclo completo, resultado y manifest de evidencia

**Fecha:** 2026-09-04
**Estado:** PASS

## 1. Objetivo

Integrar F1.19B y F1.19C en un único ciclo autoritativo que prepare el
workspace, ejecute al candidato dentro de Sandbox Runtime, realice la
verificación trusted y cierre la corrida con `result.json` y
`manifest.sha256`.

## 2. Contrato de tarea

`run-config.schema.json` incorpora el campo obligatorio `taskFile`. La ruta es
relativa al repositorio canónico y el harness rechaza rutas absolutas, escapes
fuera del repositorio, archivos ausentes o vacíos.

Antes de ejecutar al candidato se registra:

- la ruta lógica en `run.json` y `baseline.json`;
- el contenido efectivo en `task.md`;
- su SHA-256 en `baseline.json`.

Esto evita depender de una instrucción oral o de un prompt no preservado.

## 3. Preflight trusted

El orquestador `run_benchmark.py` valida de manera cerrada:

- conjunto exacto de campos de run y transport;
- versiones de contrato;
- sintaxis y existencia del commit completo;
- coincidencia de `candidateName` entre ambos contratos;
- límites de timeout;
- ruta y contenido de tarea/transporte;
- perfil `rat-default` como único perfil implementado;
- presencia de la credencial declarada para transportes cloud;
- igualdad entre los managed settings efectivos de `/etc/claude-code` y la
  copia versionada trusted.

No se copia el valor de una credencial a ningún snapshot.

## 4. Ejecución candidata

El candidato se ejecuta con Claude Code 2.1.252 dentro de SRT usando:

- política por corrida generada por F1.19B;
- `dontAsk` y managed settings efectivos;
- sesiones y Chrome deshabilitados;
- configuración, HOME y TMPDIR efímeros por corrida;
- entorno reconstruido desde una allowlist mínima, sin heredar variables
  arbitrarias del host;
- variables Anthropic-compatible derivadas del contrato neutral;
- timeout efectivo igual al menor valor entre run y transport;
- grupo de procesos independiente, terminado primero con SIGTERM y después con
  SIGKILL si no responde.

El repositorio canónico y todo `benchmark-runs` se incorporaron a `denyRead` y
`denyWrite`. Así el candidato trabaja únicamente con su clon independiente y no
puede inspeccionar el verifier, fixture ni evidencia mientras corre.

## 5. Logs y credenciales

`stdout` y `stderr` se drenan concurrentemente para impedir deadlocks y se
limitan a 16 MiB por stream sin dejar de consumir la tubería. El contenido
excedente se descarta y se marca como truncado.

Antes de persistir los logs, el harness sustituye cualquier aparición exacta de
la credencial inyectada por `[REDACTED]`. El proceso candidato recibe un entorno
mínimo y no recibe el nombre original de la variable de credencial.

Los logs se escriben atómicamente con modo `0600` en evidencia trusted.

## 6. Derivación autoritativa de estado

La tabla normativa es:

| Ejecución | Verifier | Estado |
|---|---|---|
| exit 0 | PASS | PASS |
| exit distinto de 0 | PASS/FAIL | FAIL |
| cualquier exit | FAIL | FAIL |
| timeout | PASS/FAIL | TIMEOUT |
| cualquier estado | error de infraestructura trusted | HARNESS_ERROR |

TIMEOUT prevalece sobre un eventual PASS técnico del verifier. Solo exit 0 del
candidato y todos los checks trusted en PASS producen PASS.

## 7. Resultado y manifest

`result.json` cumple el contrato 1.0 y registra identidad, baseline, exit code,
timeout, estado de checks y tiempos UTC.

`manifest.sha256` se genera al final sobre todos los archivos regulares de
evidencia excepto el propio manifest, en orden lexicográfico. Todo artefacto se
escribe de forma atómica y con modo `0600`.

La evidencia final incluye:

~~~text
run.json
transport.json
baseline.json
task.md
srt-settings.json
agent.stdout.log
agent.stderr.log
verification.json
tests.log
result.json
manifest.sha256
~~~

## 8. Validaciones realizadas

### 8.1 Ciclo exitoso controlado

Se ejecutó el ciclo completo con un proceso candidato neutro, sin inferencia ni
consumo de API. Resultado:

~~~text
agentExitCode: 0
trustedChecksPassed: true
status: PASS
manifest: todos los archivos OK
~~~

La opción interna utilizada para sustituir el ejecutable durante esta prueba se
eliminó después; la interfaz final fija Claude Code como ejecutable candidato.

### 8.2 Ejecutable fuera del workspace

SRT rechazó un script de prueba ubicado fuera del workspace legible. El
orquestador conservó la evidencia y produjo FAIL mientras el verifier técnico
permaneció en PASS. Esto confirmó que un exit no exitoso no puede convertirse
en PASS.

### 8.3 Timeout real

Claude Code real se ejecutó con un límite de un segundo y el backend local
detenido. Resultado:

~~~text
agentExitCode: null
timedOut: true
trustedChecksPassed: true
status: TIMEOUT
manifest: todos los archivos OK
~~~

No quedaron procesos Claude/SRT de la corrida ni PostgreSQL efímero después del
cierre.

### 8.4 Tests unitarios

Ocho tests cubren la matriz PASS/FAIL/TIMEOUT/HARNESS_ERROR, redacción exacta de
credenciales, permisos de logs, orden/exclusión del manifest y rechazo de un
transporte cloud sin credencial declarada.

Resultado: 8 passed.
