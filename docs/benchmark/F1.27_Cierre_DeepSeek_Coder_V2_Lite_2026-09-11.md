## Candidato y calibración de offload

- Modelo: **DeepSeek-Coder-V2-Lite-Instruct Q4_K_M**.
- GGUF: **9.65 GiB**, **15.71B parámetros**.
- Build de llama.cpp: **`5202104b5 (322)`**.
- Configuración canónica de offload para este cierre: **`-ngl 20`**.

El barrido mostró un cliff de VRAM: aumentar las capas descargadas a GPU
dejó de mejorar el rendimiento y produjo inestabilidad/degradación. `-ngl 20`
es el mejor punto operativo observado para esta evaluación, no un óptimo
universal para otros equipos o cargas.

| Offload | pp512 (tok/s) | tg128 (tok/s) / observación |
|---|---:|---|
| `-ngl 20` | 1439.40 ± 55.34 | 74.27 ± 1.48 |
| `-ngl 21` | Prefill muy inestable | Generación similar a ngl20 |
| `-ngl 22` y superiores | Degradación fuerte | Fuera de la configuración canónica |

No se asignan cifras no reportadas a ngl21 ni ngl22+.

## Inspección de template/metadata

El GGUF contiene tokens nativos de herramientas, entre ellos
`<｜tool▁calls▁begin｜>`, `<｜tool▁call▁begin｜>` y
`<｜tool▁output▁begin｜>`, junto con sus cierres. Su presencia no basta para
acreditar compatibilidad efectiva con el cliente.

La inspección reportó en llama.cpp:

```text
tool_mode: NONE
supports_tools: false
chat_format: peg-native
reasoning_format: deepseek
```

El autoparser no reconoce el template activo como compatible con herramientas.
Junto con el intento textual no ejecutado, esto sitúa el bloqueo observado en
la compatibilidad template/parser de la ruta
`Claude Code → Anthropic /v1/messages → llama.cpp → template DeepSeek`.
No demuestra una incapacidad general del modelo para usar herramientas con
otro stack; tampoco permite declarar tools operativas por tener sus tokens.
