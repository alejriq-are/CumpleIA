# F1.20B — Tarea y verifier «N/A por sección»

**Fecha:** 2026-09-04
**Estado:** PASS

## 1. Objetivo

Convertir el ítem 7 del backlog de mejoras al informe en la primera tarea
funcional del Benchmark RAT y construir un verifier trusted que distinga una
implementación correcta de una solución vacía.

## 2. Contrato de la tarea

La tarea fija un único comportamiento para todos los candidatos:

- `GET /diagnostico/actual` agrega `respondidas` y `no_aplica` a cada elemento
  de `puntaje_por_seccion`;
- `respondidas` cuenta únicamente `Sí`, `Parcial` y `No`;
- `no_aplica` cuenta únicamente `N/A`;
- respuestas ausentes o ajenas al catálogo no se cuentan;
- una sección sin respuestas devuelve cero en ambos campos;
- dashboard y HTML exportado muestran los dos conteos por sección;
- la fórmula de puntaje existente no cambia;
- no se permiten migraciones, dependencias nuevas ni cambios al harness;
- el candidato debe agregar o modificar tests de backend.

El prompt común queda en
`docs/benchmark/runner/tasks/na-section-v1.md`.

## 3. Perfil `rat-na-section-v1`

El ciclo ejecuta dos capas consecutivas:

1. `rat-default`: migraciones, fixture Módulo 1, configuración, privilegios y
   aislamiento RLS;
2. contrato N/A: cuatro pruebas funcionales y una comprobación trusted del
   alcance del diff.

La segunda capa valida:

- conteos API con respuestas mixtas y una sección vacía;
- conservación de la fórmula de puntaje con N/A fuera del denominador;
- columnas y valores por sección en el HTML exportado;
- contrato TypeScript y representación de ambos campos en el dashboard;
- presencia de tests del candidato y ausencia de cambios bajo
  `docs/benchmark/runner/`.

Un fallo de contrato produce `FAIL`. Un fallo del runtime trusted produce
`HARNESS_ERROR`.

## 4. Frontera de confianza

El verifier y sus pruebas se montan desde el checkout canónico. El workspace
candidato se monta read-only. El código candidato se ejecuta en un contenedor
separado con:

- imagen Python fijada por digest y dependencias exactas;
- red `none`;
- ninguna credencial ni conexión de base de datos;
- filesystem read-only y `/tmp` efímero `noexec,nosuid`;
- `--cap-drop ALL` y `no-new-privileges`;
- límites de 128 procesos y 256 MiB.

La inspección Git del alcance ocurre en el proceso trusted del host, no dentro
del contenedor candidato. Nunca se importa código candidato en el proceso que
posee la credencial PostgreSQL trusted.
