# F1.18D-A2 — Validación de runtime LLM local

Fecha: 2026-09-02  
Estado: VALIDADO

## 1. Objetivo

Validar el transporte local definido en F1.18D-A utilizando un runtime LLM real, con aceleración CUDA sobre la GPU del notebook, manteniendo el aislamiento de red impuesto por SRT.

La cadena objetivo validada es:

```text
Proceso dentro de SRT
  -> proxy/allowlist SRT
  -> llm-local.cumpleia
  -> 127.77.18.1:18080
  -> llama-server fuera de SRT
  -> modelo GGUF local
  -> CUDA
  -> NVIDIA GeForce RTX 5060 Laptop GPU

llama.cpp fue compilado con:
GGML_CUDA=ON
CMAKE_CUDA_ARCHITECTURES=120
CMAKE_BUILD_TYPE=Release
Las dependencias dinámicas confirmaron:

libcublas.so.13 -> /usr/local/cuda-13.1/lib64/
libcuda.so.1 -> /usr/lib/wsl/lib/libcuda.so.1
Esto mantiene la separación recomendada para WSL:
- CUDA Toolkit instalado dentro de WSL.
- Driver NVIDIA suministrado por Windows/WSL.
- No se instaló un driver NVIDIA Linux dentro de WSL.
4. Endurecimiento del transporte local
Durante F1.18D-A2 se comprobó empíricamente que allowedDomains
de SRT autoriza por hostname y no restringe por puerto.
Por este motivo no se mantuvo:
127.0.0.1 llm-local.cumpleia
Se configuró en cambio un loopback dedicado:
127.77.18.1 llm-local.cumpleia
El backend local se enlaza exclusivamente a:
127.77.18.1:18080
Esto separa el hostname autorizado de otros servicios que escuchan
específicamente en 127.0.0.1.
5. Arranque del runtime
El servidor se ejecutó con un esquema equivalente a:
llama-server
  -m Qwen3.5-0.8B-Q4_0.gguf
  --host 127.77.18.1
  --port 18080
  -ngl 99
  -c 4096
Resultado:
model loaded
listening on http://127.77.18.1:18080
6. Inferencia real fuera de SRT
Se ejecutó una solicitud OpenAI-compatible contra:
http://llm-local.cumpleia:18080/v1/chat/completions
Resultado esperado y obtenido:

La prueba confirmó inferencia real del modelo local.

11. Riesgo residual
La mitigación mediante 127.77.18.1 depende de mantener el siguiente
invariante durante el benchmark:
No deben existir servicios de aplicación escuchando en 0.0.0.0 o [::].
Un futuro servicio enlazado a una dirección wildcard podría aceptar
conexiones sobre 127.77.18.1 y quedar potencialmente alcanzable mediante
el hostname permitido por SRT.
Por tanto:
- Debe verificarse la ausencia de listeners wildcard antes de cada ejecución
  oficial del benchmark.
- El hostname local debe continuar resolviendo exclusivamente a 127.77.18.1.
- llama-server debe continuar enlazado exclusivamente a 127.77.18.1.
- No debe considerarse allowedDomains como una restricción de puerto.
Una arquitectura con namespace o aislamiento de red adicional puede
evaluarse posteriormente si se requiere una garantía más fuerte.
12. Observación de seguridad de llama-server
llama-server informó:
CORS is set to allow all origins ('*') and no API key is set
Para F1.18D-A2 esto se acepta porque:
- el servicio no está expuesto sobre interfaces externas;
- está enlazado exclusivamente a 127.77.18.1;
- SRT controla el acceso desde los procesos candidatos.
La configuración puede endurecerse posteriormente para el runner
definitivo si resulta necesario.
