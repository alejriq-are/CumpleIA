# F1.22A — Diseño de la tercera tarea funcional: selector de organización activa

**Fecha:** 2026-09-04  
**Estado:** PASS de diseño; ejecución no iniciada

## Motivación

CumpleIA ya expone `GET /me/organizations`, que devuelve únicamente las
organizaciones a las que pertenece el usuario. Sin embargo, las pantallas de
organización y autodiagnóstico consumen implícitamente el primer elemento de
esa lista. Esa suposición impide a usuarios con más de una membresía elegir el
tenant con el que quieren trabajar y puede llevar a operar sobre un contexto
equivocado.

La tarea ejercita una superficie distinta de las rondas anteriores: navegación
Next.js, tipos TypeScript, estado de interfaz y propagación segura del contexto
de tenant hacia llamadas de API ya existentes. No agrega ni modifica una ruta
backend y no altera la política RLS.

## Tarea propuesta: `active-organization-selector-v1`

Implementar un selector reutilizable de organización activa para las pantallas
`/dashboard/organizacion` y `/dashboard/autodiagnostico`.

### Contrato funcional

1. Si el usuario pertenece a varias organizaciones, ambas pantallas deben
   mostrar un control accesible que permita escoger una de sus membresías.
2. La organización activa debe estar representada explícitamente en el URL
   mediante el parámetro de consulta `organization`, para que recargar o abrir
   el enlace conserve el contexto elegido.
3. Si el parámetro no existe, se selecciona la primera membresía devuelta por
   `api.me.organizations`; si existe pero no pertenece al usuario, la pantalla
   debe usar el estado seguro de selección inicial y no debe enviar ese UUID
   arbitrario al backend.
4. La pantalla de organización debe entregar la organización activa al
   formulario; la de autodiagnóstico debe entregarla al workspace y a sus
   operaciones de diagnóstico. No puede seguir tomando implícitamente la
   posición cero cuando hay una selección válida.
5. La interfaz debe conservar los estados actuales de usuario sin
   organizaciones y de sesión no autenticada.

### Límites explícitos

- No cambiar backend, modelos, migraciones, RLS, autenticación ni contratos
  existentes de `GET /me/organizations`.
- No persistir la organización activa fuera del URL ni confiar en valores de
  cliente sin comprobarlos contra la lista de membresías del servidor.
- No modificar assets protegidos del verifier ni tests trusted.

## Diseño verificable

El futuro perfil `rat-active-organization-selector-v1` deberá comprobar:

- que ambas páginas leen y validan el parámetro `organization` contra la lista
  de membresías;
- que un UUID válido se propaga a `OrganizacionForm` y
  `AutodiagnosticoWorkspace`, y uno ajeno no;
- que existe un selector accesible con las organizaciones disponibles y que
  actualiza el URL;
- que no se rompen los estados sin sesión ni sin organizaciones;
- que el baseline actual falla por la selección implícita de la primera
  organización y una solución dorada temporal aprueba.

El verifier puede usar pruebas estáticas y de componentes aislados con
fixtures de dos organizaciones, sin requerir red, Supabase ni base de datos.
Los controles trusted comunes se conservarán encadenados a `rat-default`.

## Candidatos y comparabilidad

F1.22A no fija aún baseline, timeout ni candidatos. Esa decisión corresponde
a F1.22C, después de que F1.22B demuestre que el verifier rechaza el baseline
y acepta una solución dorada. Claude Sonnet 5 queda como referencia por ser el
único PASS de F1.21; Qwen3-4B local no debe interpretarse como candidato
principal para esta tarea tras sus dos FAIL funcionales. La incorporación de
un modelo local mayor requiere un preflight separado y compatible con la VRAM
disponible.

## Criterio de salida de F1.22A

El diseño está listo para F1.22B cuando el verifier pueda expresar todos los
cinco puntos del contrato sin depender de una implementación candidata ni de
servicios externos.

baseline negativo y solución dorada temporal.
