**Predecesor:** F1.18C — Transporte cloud DeepSeek / PASS

## 1. Objetivo

Validar una arquitectura de transporte que permita a un proceso ejecutado
dentro de SRT acceder a un backend LLM ejecutado localmente, sin habilitar
acceso general a localhost, sin habilitar Unix sockets arbitrarios y sin
debilitar el aislamiento de red validado en F1.16–F1.18C.

Esta etapa valida exclusivamente la arquitectura de transporte.

No se instala todavía un runtime LLM ni se descarga un modelo local.

3. Primera arquitectura evaluada — Unix Domain Socket
Inicialmente se evaluó utilizar un Unix Domain Socket dedicado:
/home/cumplebench/runtime/local-llm/test.sock
Se creó un servidor de prueba Python fuera de SRT.
El socket fue creado correctamente con permisos 600 y el proceso Python
quedó escuchando sobre esa ruta.
3.1 Control negativo
Con:
"allowUnixSockets": []
un cliente Python ejecutado dentro de SRT falló al intentar crear un socket
AF_UNIX:
PermissionError: [Errno 1] Operation not permitted
Resultado: PASS.
SRT bloqueaba correctamente los Unix sockets por defecto.
3.2 Prueba con allowUnixSockets
Se agregó temporalmente:
"allowUnixSockets": [
  "/home/cumplebench/runtime/local-llm/test.sock"
]
manteniendo:
"allowLocalBinding": false
La prueba continuó fallando en la creación del socket:
PermissionError: [Errno 1] Operation not permitted
3.3 Conclusión de la primera arquitectura
La autorización selectiva de un Unix Domain Socket no resultó viable con
SRT en Linux.
El mecanismo de aislamiento Linux bloquea AF_UNIX mediante seccomp antes de
que pueda aplicarse una decisión basada en la ruta del socket.
No se habilitó allowAllUnixSockets, porque otorgaría una capacidad más
amplia que la requerida y sería incompatible con el principio de mínimo
privilegio del benchmark.
La política SRT fue restaurada al estado seguro anterior.
4. Arquitectura v2 — endpoint local mediado por proxy SRT
Se diseñó una segunda arquitectura basada en el mecanismo de proxy y
allowlist ya utilizado por SRT para Anthropic y DeepSeek.
Arquitectura conceptual:
Proceso dentro de SRT
        |
        | HTTP mediante proxy SRT
        v
llm-local.cumpleia
        |
        | resolución local controlada
        v
127.0.0.1:18080
        |
        v
Servidor LLM local
El objetivo es que el proceso sandboxed no pueda acceder directamente a
localhost y que solamente pueda alcanzar el backend mediante un hostname
explícitamente autorizado.
5. Inspección del entorno de proxy SRT
Dentro de SRT se verificó la presencia de:
- HTTP_PROXY;
- HTTPS_PROXY;
- ALL_PROXY;
- sus equivalentes en minúsculas.
Los proxies apuntaban al mecanismo interno SRT en localhost:3128.
También se verificó que NO_PROXY incluía localhost, loopback y rangos
privados.
Esto confirmó que SRT dispone de una capa propia de mediación del tráfico
HTTP/HTTPS.
6. Servidor HTTP local de prueba
Se levantó fuera de SRT un servidor HTTP Python:
127.0.0.1:18080
El acceso directo desde WSL normal produjo:
HTTP=200
Resultado: PASS.
7. Hostname local controlado
Se configuró temporalmente:
127.0.0.1 llm-local.cumpleia
Fuera de SRT:
http://llm-local.cumpleia:18080/
produjo:
HTTP=200
Resultado: PASS.
8. Control negativo de allowlist
Antes de autorizar llm-local.cumpleia, se intentó acceder al hostname
desde dentro de SRT.
Resultado:
HTTP=403
Resultado: PASS.
El hostname local quedó sometido a la allowlist de SRT y no permitió
bypass de la política.
9. Autorización explícita del backend local
Se agregó exclusivamente:
llm-local.cumpleia
a allowedDomains.
La política resultante fue:
{
  "allowedDomains": [
    "api.anthropic.com",
    "platform.claude.com",
    "api.deepseek.com",
    "llm-local.cumpleia"
  ],
  "deniedDomains": [],
  "allowUnixSockets": [],
  "allowLocalBinding": false
}
No se habilitaron Unix sockets.
No se habilitó local binding.
10. Prueba positiva dentro de SRT
Desde dentro de SRT:
http://llm-local.cumpleia:18080/
produjo:
HTTP=200
Resultado: PASS.
Esto demuestra que SRT puede alcanzar el servicio local mediante un
hostname explícitamente autorizado.
11. Controles negativos posteriores
11.1 Acceso directo a localhost
Desde dentro de SRT se intentó:

HTTP=000

Resultado: PASS.
La autorización de llm-local.cumpleia no abrió acceso general a localhost.
11.2 Segundo hostname no autorizado
Se configuró temporalmente:

Esto demuestra que la autorización depende del hostname explícitamente
incluido en la allowlist y no solamente del destino IP o puerto.

13. Resultado
F1.18D-A: PASS ARQUITECTÓNICO
Se validó una arquitectura que permite transportar solicitudes desde un
proceso ejecutado dentro de SRT hacia un backend local, manteniendo el
control mediante la allowlist de SRT.
El backend local deberá:
1. ejecutarse fuera del sandbox;
2. escuchar exclusivamente sobre loopback;
3. exponerse al sandbox mediante un hostname dedicado;
4. requerir que dicho hostname esté explícitamente autorizado por SRT.
La arquitectura evita habilitar acceso general a localhost y evita
habilitar Unix sockets arbitrarios.
14. Arquitectura seleccionada
